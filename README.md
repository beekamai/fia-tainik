# Тайник

**Zero-knowledge самоуничтожающиеся заметки для сообщества fia.li.**

Пользователь пишет секрет, **браузер шифрует его на клиенте**, сервер хранит
только шифротекст в Redis с TTL. Получатель открывает одноразовую ссылку,
раскрывает заметку один раз — и она сгорает. Сервер **никогда** не видит ни
текста, ни ключа.

Это ещё и **референс-репозиторий**: показывает, как собирается приложение
сообщества fia.li (Bun + Elysia + Redis), как оно подключается к платформе
через манифест, S2S-лимиты и проброшенный токен авторизации. Код намеренно
маленький и подробно прокомментирован — читайте `backend/src`.

> Sibling-приложение [`redirects`](../redirects) — более полный пример (с
> Postgres/Drizzle и вендоренным SDK). Тайник проще: **только Redis, без БД,
> без SDK** (две вызова к fia.li сделаны обычным `fetch`).

## Модель безопасности (zero-knowledge)

Главная идея: **доверие к серверу не требуется**. Даже полный дамп Redis не
раскроет ни одной заметки.

```
            СОЗДАНИЕ                                  РАСКРЫТИЕ
  ┌─────────────────────────┐            ┌──────────────────────────────┐
  │ браузер автора          │            │ браузер получателя           │
  │                         │            │                              │
  │ 1. генерит случайный    │            │ 5. достаёт ключ из           │
  │    ключ (AES-GCM)       │            │    #фрагмента ссылки          │
  │ 2. шифрует текст        │            │ 6. POST /reveal → ciphertext  │
  │ 3. POST /notes          │            │ 7. расшифровывает локально    │
  │    { ciphertext, ttl }  │            │                              │
  └───────────┬─────────────┘            └───────────────┬──────────────┘
              │  ciphertext                               │ ciphertext
              ▼                                           ▼
       ┌──────────────────────── СЕРВЕР (этот репозиторий) ───────────────┐
       │  Хранит ТОЛЬКО ciphertext в Redis с TTL.                          │
       │  При раскрытии — атомарный GETDEL: отдал и удалил за одну         │
       │  операцию (read-once burn). Plaintext и ключ сюда не попадают.    │
       └───────────────────────────────────────────────────────────────────┘

  Ссылка:  https://tainik.fia.li/n/<id>#<base64url-ключ>
                                  └─id─┘ └──── ключ ─────┘
                                  идёт    остаётся в браузере,
                                  на      НЕ отправляется на сервер
                                  сервер  (URL fragment)
```

Почему это работает:

- **Ключ живёт во фрагменте URL (`#...`).** Браузеры не отправляют фрагмент на
  сервер — он доступен только клиентскому JS. Сервер физически не может его
  получить.
- **Шифрование на клиенте (AES-GCM через WebCrypto).** Сервер получает уже
  готовый шифротекст и хранит его как есть. **В этом репозитории нет ни одной
  строки серверного шифрования — и не должно быть.** Любая попытка «дошифровать
  на сервере» ломает гарантию zero-knowledge.
- **Read-once burn через `GETDEL`.** Redis отдаёт значение и удаляет ключ за
  одну атомарную операцию. Две одновременные попытки раскрытия не могут обе
  выиграть — ровно одна получит шифротекст, остальные получат `404`.
- **TTL.** Непрочитанная заметка автоматически исчезает по истечении срока —
  чистка не нужна, это делает сам Redis.

> Фронтенд (шифрование, разбор фрагмента, UI) — отдельно. Этот репозиторий —
> бэкенд: хранилище и принуждение лимитов плана. Контракт между ними — поле
> `ciphertext` (непрозрачный base64) и `id` в ссылке.

## API

Базовый префикс: `/api/tainik`.

### `POST /api/tainik/notes` — создать заметку

**Требует авторизации** (см. «Авторизация» ниже). Единственный защищённый
маршрут — нужно знать автора, чтобы применить лимиты его плана.

```jsonc
// Request body
{
  "ciphertext": "<base64 client-encrypted blob>",
  "ttlHours": 24            // желаемый срок; обрезается до потолка плана
}
```

```jsonc
// 200 OK
{
  "id": "3f2a...e1",        // 32 hex-символа, идёт в ссылку
  "ttlHours": 24,           // фактический TTL после клампа под план
  "expiresAt": "2026-06-24T12:00:00.000Z"
}
```

Ошибки: `401` (нет/невалидный токен), `403` (превышен дневной лимит плана),
`413` (шифротекст больше лимита плана), `422` (тело не прошло валидацию).

### `GET /api/tainik/notes/:id` — проверка существования (НЕ сжигает)

**Публичный, неразрушающий.** Для экрана «раскрыть заметку?» у получателя и
чтобы превью-боты мессенджеров не сожгли заметку случайно. Возвращает только
факт наличия.

```jsonc
{ "exists": true }
```

### `POST /api/tainik/notes/:id/reveal` — раскрыть и сжечь

**Публичный, атомарный.** `GETDEL` за одну операцию отдаёт шифротекст и удаляет
заметку — одноразово.

```jsonc
// 200 OK — первый и единственный раз
{ "ciphertext": "<base64 client-encrypted blob>" }

// 404 — нет заметки / уже прочитана / истёк TTL
{ "message": "Note not found or already read" }
```

### Служебные

- `GET /health` → `{ "status": "ok", "ts": <ms> }` — для Docker HEALTHCHECK и LB.
- `GET /manifest` → манифест сервиса (см. ниже).

## Интеграция с fia.li

Тайник не управляет собственными аккаунтами и тарифами — он опирается на
платформу. Три точки сопряжения:

### 1. Манифест (`GET /manifest` + `manifest.json`)

Реестр fia.li читает манифест, чтобы узнать, какие возможности (лимиты) у
сервиса настраиваемые. Тайник объявляет три:

| key              | label                 | default |
|------------------|-----------------------|---------|
| `maxNotesPerDay` | Заметок в день        | `10`    |
| `maxTtlHours`    | Макс. срок жизни (ч)  | `24`    |
| `maxNoteSizeKb`  | Макс. размер (КБ)     | `32`    |

`-1` в числовом лимите = безлимит. Манифест в коде (`index.ts`) и в корневом
`manifest.json` держатся синхронными.

### 2. Лимиты по плану (S2S, HMAC)

При создании заметки бэкенд тянет лимиты пользователя из billing-сервиса
service-to-service:

```
GET {BILLING_URL}/internal/user/:userId/services/tainik/limits
```

Запрос подписывается HMAC-SHA256 (`backend/src/services/s2s.ts`), схема —
как в `@fia-li/core`:

```
X-Service-Name:      tainik
X-Service-Timestamp: <ms>
X-Service-Signature: base64url(HMAC-SHA256(`${ts}:tainik:GET:/internal/user/<id>/services/tainik/limits`, INTERNAL_SECRET))
```

Подпись привязана к методу и пути (`{ts}:{service}:{METHOD}:{path?query}`), так что
перехваченную подпись нельзя повторить на другом эндпоинте. `tainik` должен быть
в allowlist `ALLOWED_SERVICES` ядра fia.li (fia-li/system ≥ #12).

Если billing недоступен или у пользователя нет записи плана для Тайника —
включается безопасный фолбэк `FREE_LIMITS` (`backend/src/services/limits.ts`).
**S2S-вызов никогда не бросает исключение** — сбой биллинга не должен ронять
создание заметки.

### 3. Авторизация (проброшенный токен)

Платформа пробрасывает учётку пользователя, бэкенд валидирует её через fia.li
`GET /me` (`backend/src/plugins/auth.ts`). Токен берётся из:

- `Authorization: Bearer <token>` (API-клиенты), **или**
- `Cookie: access_token=<token>` (браузерная панель).

Профиль кэшируется в Redis на короткий срок (`AUTH_CACHE_TTL`, по умолчанию
30 с) под хешем учётки — всплеск запросов превращается в один вызов `/me`.

## Переменные окружения

См. `.env.example`. Кратко:

| Переменная        | Default                 | Назначение                                  |
|-------------------|-------------------------|---------------------------------------------|
| `PORT`            | `3110`                  | Порт HTTP-сервера                           |
| `FIALI_BASE_URL`  | `https://api.fia.li`    | fia.li API для `/me`                        |
| `BILLING_URL`     | `http://billing:3003`   | Internal API биллинга (S2S)                 |
| `INTERNAL_SECRET` | `""`                    | HMAC-секрет S2S (пусто = только FREE-лимиты)|
| `REDIS_HOST`      | `redis`                 | Хост Redis                                  |
| `REDIS_PORT`      | `6379`                  | Порт Redis                                  |
| `REDIS_PASSWORD`  | —                       | Пароль Redis                                |
| `ALLOWED_ORIGINS` | `https://panel.fia.li`  | CORS-origins через запятую                  |
| `AUTH_CACHE_TTL`  | `30`                    | TTL кэша `/me` в секундах                   |

## Запуск

Нужен **[Bun](https://bun.sh)** и работающий **Redis**.

```bash
cp .env.example .env       # заполни значения (как минимум REDIS_HOST)
bun install
bun run dev                # автоперезапуск на изменениях
# или
bun run start
```

Проверка:

```bash
curl localhost:3110/health
curl localhost:3110/manifest
```

## Деплой (Docker)

Образ — пиннутый `oven/bun:1.2.23-alpine`, мультистейдж, со встроенным
HEALTHCHECK на `/health`.

```bash
docker build -t fia-tainik .
docker run -p 3110:3110 \
  -e REDIS_HOST=your-redis-host \
  -e INTERNAL_SECRET=... \
  fia-tainik
```

> Для воспроизводимых сборок закоммить `bun.lock` (`bun install` сгенерирует
> его). Dockerfile использует `--frozen-lockfile`; `bun.lock*` в `COPY`
> опционален, чтобы сборка не падала, пока лок-файла нет.

## Структура

```
tainik/
├── manifest.json              # манифест сервиса (= то, что отдаёт /manifest)
├── package.json               # single package: elysia, @elysiajs/cors, ioredis
├── tsconfig.json
├── Dockerfile                 # oven/bun:1.2.23-alpine, multi-stage
├── .env.example
└── backend/src/
    ├── index.ts               # Elysia app: cors, /health, /manifest, onError
    ├── config.ts              # вся работа с process.env — здесь
    ├── errors.ts              # HttpError
    ├── redis/client.ts        # ioredis-клиент + билдеры ключей
    ├── plugins/auth.ts        # derive: /me-валидация проброшенного токена
    ├── routes/notes.ts        # create / probe / reveal (вся бизнес-логика)
    └── services/
        ├── s2s.ts             # HMAC S2S-клиент к биллингу (never throws)
        └── limits.ts          # лимиты плана + квоты/кламп/размер
```
